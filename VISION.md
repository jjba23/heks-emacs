# Vision

`heks-emacs` is a modular Emacs configuration that treats its own documentation as an output: the keybindings reference is written from the key tables by `maak keys-update`, `maak keys` fails while the two disagree, and the golden pages and the batch verification load the configuration the way Emacs does and assert what follows. That is the thing worth building on — not that it is a good configuration, but that it is a configuration that can be held to itself. This document is about extending that discipline from the keys to the modules, the palettes, the startup and the notes, so the parts of the README that are prose become parts that are checked.

## Where heks-emacs is today

Fifty-five modules under `src/modules/`, one topic per file, loaded in the order `init.el` declares, after `early-init.el` has set up Elpaca and after a bridge file — `heks-linux-bridge.el` or `cask-and-cons-bridge.el` — has been read, because the modules read their settings while they are being set up rather than being configured later. The numbers the README quotes are refreshed by `maak stats` from a batch Emacs: over 140 packages, over 500 functions, over 110 interactive commands, over 50 customization variables, more than 180 ERT tests, over 32 themes and over 200 snippets. The modules are grouped by what a person does rather than by what Emacs calls things: core, UI and palettes, development (the languages, their language servers, `sift`, Git, GitHub, onefetch), Org and knowledge (`notes`, `notes-graph`, `notes-auto`, `agenda`, `bookmarks`, `contacts`), shell and system, search and navigation, mail, music and maps, writing and rendering, the libraries, and AI.

The key scheme is the part with a specification behind it. Every key the configuration adds lives under `C-c`, a letter for the topic and a letter for the action, and the action letters mean the same thing under every topic — `f` formats, `t` tests, `g` goes to a definition, `k` stops a process, `i` inserts. The tables in `emacs-core.el` are the scheme: `heks/key-topics`, `heks/key-actions`, `heks/key-letters` and `heks/key-descriptions`. The last one exists because a letter can only say so much: `C-c i f` and `C-c j f` both format, but one is "the buffer, formatted by whoever knows how", and a key that said only "format" would leave the reader guessing. `test/heks-emacs-keys.el` reads all four, prints the key tree, writes `docs/keybindings.org`, and refuses a binding whose topic is not described, whose command does not exist, whose letters are in no table, or that has no sentence of its own. `which-key` is taught the same tables, so a key that is being learned is explained while it is pressed.

The checks are a ladder with a clear deliberate shape. `maak lint` reads every Elisp file form by form and compares the module list in `init.el` with the modules that exist — no packages needed, a parenthesis that closed a macro too early and a module renamed without its entry are both caught there. `maak render` renders the documents, `maak test` runs the ERT suite, `maak golden` compares the golden pages, `maak verify` installs the configuration and then loads it the way Emacs does at startup, asserting its invariants: every module loaded, a fold covers a whole definition, a checker survives a tool's decorated output, nothing breaks without Guix, a Markdown file renders, an OpenAPI file is read and checked. `maak check` runs the lot. The numbers in the NEWS entries — lint 172, keys 0 findings, render 33, golden 5 matched, verify 430 — are what that ladder reports, and quoting them per release is the habit that keeps them honest.

The notes system is the other half of the project's identity. One Org file per note, no database; `todo.org` with an inbox, `habits.org` with repeaters, index pages per topic generated from the files, an agenda, a graph page, bookmarks, contacts and a diary. `docs/notes.org` documents the philosophy, the layout, every file format, each workflow, syncing, tweaking and an FAQ — and the same formats are read and written from the shell by the `n` command in `heks-bash`, which writes index pages byte-identical to the ones Emacs writes. Moving a note is deliberately left to Emacs, because it has to repair the links that point at it.

Three more things are worth naming because they are the configuration's character rather than its features. `docs/github-repo.org` records the GitHub repository settings as a spec with three commands to capture, apply and verify them — the repository's own settings, treated like everything else here. `C-c r p` previews a Markdown file, an Org note, an OpenAPI specification or a plain text file as a themed HTML page with no network, and `C-c r P` turns the same document into a deck. And the AI story is two front ends, GPTel and ECA, over DeepSeek or Copilot, with `auto`, `HEKS_AI_PROVIDER` or `heks/ai-provider` deciding which, and `C-c x p` moving a session to the other without a restart.

What is not checked is as visible as what is. The key scheme is enforced; the *module* rule is prose — "the module owns the topic", a key about notes goes in `notes.el` — and nothing verifies it. Palettes are claimed to derive their faces, separators and prose sizes from the theme so that nothing goes invisible when you switch, and no test asserts a contrast ratio. Startup is measured by `maak stats` and `rc-time` in the shells, but nothing gates on it. And the package set is pinned by Elpaca's own state under `~/.emacs.d/elpaca`, not by a lock file in the tree, so what is reproducible is the bootstrap rather than the installation.

## The vision

1. **Every module is a declaration, and the declaration is checked.** A module says which topic it owns, which keys it binds, which commands it defines and which variables it reads; `maak check` fails when a key is bound outside the module that owns its topic, when a module binds a key it did not declare, or when a bridge sets a variable that no module reads. The key table becomes one instance of a general contract.

   What has to be true first: a per-module shape — a `defheks-module` form or a table beside each file — that the loader, the reference generator and the tests can all read.

2. **The documentation is generated wherever it can be.** `docs/keybindings.org` already is. `docs/modules.org`, `docs/configuration.org` and the module tables in the README should be too, from the declarations above, so that a module cannot exist without a paragraph and a variable cannot exist without a default that is written down once.

   What has to be true first: the declarations, because a document can only be generated from something that is data.

3. **The palettes are tested, not promised.** Every one of the 32-odd themes is loaded in a batch Emacs and the faces the configuration derives are checked for contrast and for the absence of the classic failure — a face that inherits nothing and lands on the background colour. `maak themes` would be the check that makes "nothing goes invisible when you switch" a fact.

   What has to be true first: a way to compute a contrast ratio in Elisp from a face's resolved attributes, which is arithmetic over `color-values`.

4. **Startup and the edit path have budgets.** A number for startup, a number for the slowest module, and a number for the first `C-c` — measured on every check, reported by `maak stats`, and failing when a change makes the editor slower. A configuration that is delightful at day three hundred is one that did not quietly accumulate a second of startup.

   What has to be true first: a stable measurement in batch, which means `emacs -Q --batch` and a median over runs rather than a single number.

5. **The installation is reproducible, and the check says so.** The package set has a lock in the tree, a `maak verify` that installs from it with no network, and a reported diff when a package moves. Today the bootstrap is pinned and the installation is whatever Elpaca last fetched.

   What has to be true first: Elpaca's state promoted from `~/.emacs.d/elpaca` into the repository, and a decision about how a package update is reviewed.

## Features that are in scope and not built yet

The design anticipates these; each is a seam the current design leaves open.

- **The module contract.** The key tables exist and the module rule does not. The hard part is that a module's topic is currently implied by its filename and its prose, so enforcing it needs a declaration that a contributor will actually keep up to date.
- **A contrast check over the palettes.** The claim is made in the README and the mechanism (faces derived from the theme) is already there. The hard part is the arithmetic: a face's resolved foreground can be `unspecified` or inherited twice, and the check has to resolve it the way the display would.
- **Golden pages for the workflows that have none.** Five pages are goldened; mail, IRC, the agenda and the notes graph are not. The hard part is that a golden page for a workflow whose content is time-dependent needs a frozen clock, which Emacs makes possible and nobody has done here.
- **A lock file for the package set.** Elpaca has the state; the repository does not. The hard part is a reviewable diff when 140 packages move at once, which argues for pinning per package rather than per snapshot.
- **An offline install.** `maak verify` installs the configuration and needs the packages already present. The hard part is Elpaca's first-run bootstrap, which fetches recipes over the network — a lock would let the first run be a cached one.
- **A startup profile in `maak stats`.** `emacs --batch -g 0` gives a per-file cost. The hard part is turning a profile into a budget that does not fail on a slow CI machine.
- **A bridge schema.** A bridge sets `heks/font-mono`, `heks/theme`, `heks/notes-dir` and the rest. The hard part is telling a typo from a variable a future module will read, which is the same problem the key audit solved with a sentence per key.
- **`docs/modules.org` generated from the modules.** The hardest of the documentation generators, because a module's paragraph is an argument rather than a datum, and only the structure of it can be generated.
- **A startup profile as a document.** `maak stats` prints line counts and decision points; the profiler prints cost per file. The hard part is that a profile is only comparable across runs on the same machine, so the useful artefact is a relative report — which module is expensive compared with its size — rather than an absolute table.
- **A test that the configuration loads with every optional tool absent.** `maak verify` asserts that nothing breaks without Guix, which is the right instinct applied once. The hard part is enumerating the set: no `rg`, no language servers, no `sift`, no `eca-cli`, no tree-sitter grammars — and a configuration where every module still loads and says what it is missing.
- **The bridges as a declared interface.** `heks-linux-bridge.el` and `cask-and-cons-bridge.el` are two files on the other side of the fence, and `docs/configuration.org` documents every variable a bridge may set. The hard part is that the bridge is loaded before the modules that read it, so a check has to run between the two.
- **A fold that survives an edit.** `verify` asserts that a fold covers a whole definition, which is the configuration's own answer to Elisp's folding being approximate. The hard part is the same one the check already meets: a fold that is correct in batch is not necessarily correct after a structural edit, so the assertion has to be cheap enough to run on save.
- **The deck, as a golden.** `C-c r P` turns a document into a deck and nothing compares the output. The hard part is that a deck is HTML with a theme, so the golden has to pin the theme too — which is exactly the kind of decision the existing goldens already made.

## New features that would be worth having

- **`C-c` on a key explains it in place.** `heks/key-descriptions` already holds a sentence per key and `which-key` already shows them while a prefix is being typed. The same table, a command that echoes the sentence of the key at point, would make the scheme teachable from any buffer rather than only from `docs/keybindings.org`.
- **A `heks-doctor`.** Which external programs the configuration expects — `rg`, `fd`, `aspell`, the tree-sitter grammars, `sift`, `eca-cli`, Guile and Geiser's `guile` — with versions and what each module does without it. `dev-tools` already checks for them at load time; a report is the same knowledge, said once.
- **A notes query.** The notes are files and the graph is a page. A command that asks a question — every note tagged `engineering` that has an open `TODO` and has not been touched in a month — is what a file-based system needs to stay usable past a few hundred notes, and it is a `grep` plus a struct, not a database.
- **A deck that is a document.** `C-c r P` already turns a document into a deck. A theme for the deck, one that follows the palette the desktop is wearing, would make the one feature that leaves Emacs look like it came from Emacs.
- **A per-project AI provider.** `C-c x p` moves a session between DeepSeek and Copilot. Recording the choice per project — a `.dir-locals.el` entry, or a line in the project's notes — is a small feature with a large effect on what it feels like to work across several repositories.
- **A journal entry from the agenda.** The notes system has a diary topic and an agenda. A key that opens today's entry, creating it from the template if it does not exist, is the smallest possible feature and the one most likely to be used every day.
- **A theme gallery.** Thirty-two palettes and a renderer that writes HTML with no network: a page that renders one buffer in every theme, generated by `maak`, would make choosing a palette a comparison rather than a sequence of `M-x load-theme`.
- **A module's worth of notes in one command.** The notes are one file per note with generated indexes; `C-c n` is a topic with many keys. A single transient menu over the notes topic — capture, find, today, this week's agenda, the backlinks of this note — would make the largest topic in the configuration also the most discoverable, and the keys already exist to hang it on.
- **An `about` for the configuration.** Which Emacs, which modules are loaded, which palette, which font, which provider the AI is using, and the version of the configuration itself: one buffer, the answer to "what am I running", which is the question a bug report starts with and the one the current README answers in prose.
- **A `C-c` tour for a new user.** The README offers a five-minute tour of what to press first, in prose. A command that walks the five keys a beginner needs — the dashboard, notes capture, the search, the project, the renderer — with which-key open beside it, is the same tour made executable, and the sentences it needs are already written.

## Contributions that would move the needle

Ranked roughly by value per hour.

1. **The `heks/key-descriptions` echo command.** One command and one binding, in the one place the configuration already documents every key, and it makes the scheme usable without a manual.
2. **The palette contrast check.** One test file, `color-values`, and a claim in the README turned into a fact. It is the highest-value-per-hour item on this list after the key echo, and the failure it prevents is the one a reader notices first.
3. **`heks-doctor`.** The list of external programs the modules expect, with versions and fallbacks, is data that already exists in `dev-tools` and in the README's requirements.
4. **A golden page for the agenda and for mail.** The pattern exists; what is missing is a frozen clock and a fixture mailbox, and both are cheap in a batch Emacs.
5. **The module declaration.** The largest item here, and the one that unlocks the generated `modules.org`, the ownership check and a bridge schema. It is worth starting with a table in one module and a test that reads it.
6. **A lock file for the packages.** Valuable and unglamorous: it changes what a fresh install costs and what a review of a package bump looks like.
7. **A startup budget in `maak stats`.** The measurement exists; the discipline of failing on it does not.
8. **The theme gallery.** Small, delightful, and it makes the palette work visible in a way that 32 names in a table never will.
9. **`heks-doctor`'s table in the README.** The programs, their purpose and what happens without each is a table anyone can write from the modules, and it is the documentation a person needs before they run `maak verify` on a new machine.
10. **A golden page for the renderer's four inputs.** Markdown, Org, OpenAPI and plain text are the four things `C-c r p` accepts, and one of them is goldened. The other three are the same test with a different fixture.
11. **The `C-c x` provider story as a table.** Two front ends, two accounts, three ways to choose a provider and one key to move a session. `docs/ai.org` has the prose; the table is what a reader looks for when a provider fails to answer.

## Compared to related projects

| Project | What it is | Where heks-emacs differs |
|---|---|---|
| Doom Emacs | A macro-assembled, opinionated framework with Evil keybindings, a module system and a large curated package set | Doom is a framework you install and configure; this is a configuration you move into. Doom's modules are macros that assemble a config, and its documentation is written about the modules. Here the reference is generated from the keys and the checks fail when the two disagree |
| Spacemacs | An Evil-first configuration with layers, a mnemonic key scheme (`SPC`-led) and a large community | The nearest philosophical relative: a key grammar and layers of configuration. The difference is the grammar — `C-c` with an action alphabet that means the same thing under every topic — and the fact that the grammar is data with a test rather than a convention |
| Prelude | A curated, minimal Emacs configuration, closer to a set of sensible defaults than a framework | Prelude is deliberately small and asks little of the user. This one is deliberately large and asks to be read: every module argues its decisions in the comments beside them, and the README recommends browsing the source over using it |
| Centaur Emacs | A batteries-included configuration aimed at being usable out of the box, with a Chinese-language community around it | Same ambition — a working environment on day one — and a different answer to the documentation question: Centaur explains what it includes, this generates a reference from what it binds and gates on the difference |
| Crafted Emacs | A literate, modular configuration that teaches as it configures, with a companion guide | The closest in spirit to "read it and learn": Crafted writes its modules as literate Org. Here the modules are Elisp with an argument beside every non-obvious decision, and the documentation is generated from the code rather than written around it |
| Purcell's `emacs.d` | A long-maintained, minimal personal configuration that many people have read and copied | The ancestor of every configuration like this one. It is stable and quiet; heks-emacs is a research project about how much of a configuration can be checked |
| Elpaca, `straight.el` | Package managers that build packages from source and pin them by commit, rather than installing from a package archive | Dependencies, not competitors. Elpaca's state is what a lock file would promote into the repository, and the comparison is the same one Guix users make about pins |
| `use-package`, `setup.el` | Declarative macros for configuring and loading packages | The vocabulary this configuration is written in. The difference is what is built on top: a key scheme, a reference generator, golden pages and a verification suite |

The others do three things this project could add. Doom's module system is the mature version of what the module declaration here would be: a module that says what it provides and what it expects, so composition is checked rather than hoped for. Crafted's literate style is a real answer to the documentation question, and the reason this project's answer has to be generation rather than prose — a literate module cannot drift from its module, and a generated reference cannot drift from its table. And the community configurations' starter kits are the thing a person actually wants first: a way to try the configuration without committing a home directory to it.

That last point deserves a sentence of its own, because it is the one criticism that lands. The README says this is "a place you move into, not a package you install", and it is honest about the cost: one command, a couple of restarts while the packages resolve. Doom, Centaur and Spacemacs all offer a way to look before you leap, and a configuration that asks for `~/.emacs.d` asks for a lot. A branch that installs into a directory of your choosing, with a launcher that runs it as a separate profile, is the smallest version of that courtesy — and it is achievable here because `maak install-emacs-config` is already a copy into a variable.

Where `heks-emacs` is ahead and should stay ahead: a key scheme with an action alphabet, a sentence for every key, and a test that fails when one is missing; documentation generated from the code in the one place it can be, with the intent to extend it; a verification suite that loads the installed configuration and asserts invariants rather than loading the source; golden pages, which almost no configuration has; and modules that argue their decisions in the comments next to them, which is why the README says to read the source rather than skim the feature list.

## In the long run

- **A configuration that is its own specification.** The end of the road this document describes is a repository where the keys, the modules, the variables and the palettes are declarations, the documentation is their rendering, and the checks are the difference between the declaration and the behaviour. That is a small, unglamorous kind of software engineering applied to a personal editor, and almost nobody does it.
- **Emacs as the operating system it nearly is.** The README calls this configuration "almost an operating system unto itself": mail, notes, music, maps, the shell, the web browser's worth of rendering, and now two AI front ends. The bet is that the interesting work moves from adding a package to making the pieces agree — one key scheme, one palette, one notes format, one place a setting lives.
- **Notes that outlive the editor.** One Org file per note, index pages, a graph and a shell command that writes the same bytes. The bet is that the format stays plain, documented and implementable from outside Emacs, which is what makes it an archive rather than a feature.
- **Reproducibility that reaches the packages.** Over 140 packages from source with no lock in the tree is the one part of this configuration that a Guix user would find alarming. The bet is that a lock, an offline install and a reviewable bump arrive, because the rest of the collection already works that way.
- **A configuration people read.** The README recommends reading the source, and the modules argue their decisions in place. The bet is that this stays the point: not a framework to adopt, but a worked example of how far a configuration can be held to its own claims.
- **A separate profile, so trying it costs nothing.** `maak install-emacs-config` copies into `~/.emacs.d`, which is the one thing this configuration asks of a stranger. The bet is that the copy becomes a parameter — a directory, a profile, a launcher — so a reader can run this editor without moving house, and the `emacs` they already have stays as it was.
- **Documentation as a build output.** One reference is generated today and the intent is that more are. The bet is that the drift between what a configuration does and what it says becomes structurally impossible for the parts that can be derived, and that the parts that cannot — a module's argument, a design decision — are where the writing goes instead of a feature list.

## A closing note

The distinguishing decision here is that every key needs a sentence, and the build fails without one. It looks like a small rule about documentation; it is really a rule about design, because a key that cannot be described in the words of its topic is a key that does not belong under that topic. Everything above — the module declaration, the generated reference, the palette check, the doctor — is that rule applied to something other than keys.

The second thing is the shape of the checks: nine tasks, each with one job and a name that says which, from `lint` reading the source without installing anything to `verify` loading the installed configuration and asserting its invariants. That ladder is why a change can be made with some confidence on a laptop and by someone else in a container, and it is the part of this project most worth copying into any configuration that has grown past a single file.

*This document describes intent, not commitments: it names directions the maintainer finds worth taking, and nothing here is a promise that a given feature will exist, in the order listed, or at all.*
