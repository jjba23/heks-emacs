#+title: Debugging
#+author: Josep Bigorra
#+options: toc:2

Four kinds of program are debugged here, and each has the same shape: one
key starts the program with a debugger attached, the session's own keys are
the same for all four, and everything the debugger cannot guess -- which
binary, which main class, which environment, which crate -- is a setting
with a name.  This page is how to use it, and what to do when a session
does not start.

* What is set up, and where

| What | Where it lives | What drives it |
|------+----------------+----------------|
| Guile Scheme, and Artanis | ~guile.el~ | Geiser's REPL, Guile's traps and its debugger commands |
| C, C++ and GTK 4 | ~dev-formats.el~ | `dape` over `gdb --interpreter=dap`, or GUD |
| Rust | ~rust.el~ | `dape` over `lldb-dap` or a `gdb` that speaks DAP, or GUD with `rust-gdb` |
| Java, Kotlin, Maven and Gradle | ~heks-emacs.el~ | `dape` over Eclipse `java-debug` |

A debug session is one topic, ~C-c b~, whichever debugger is behind it:
once something is stopped, ~C-c b b~ toggles a breakpoint, ~C-c b c~
continues, ~C-c b n~ steps over, ~C-c b i~ steps in, ~C-c b o~ steps out,
~C-c b r~ opens the debugger's prompt and ~C-c b k~ ends the session.

Those seven keys ask *whichever* debugger is live rather than naming one
(`heks/debug--dape-p', `heks/debug--gud-p', `heks/debug--scheme-p'), so the
hand that learned them on a C program knows them in a Scheme buffer, in a
Rust crate and in a JVM.  What differs is only the key that *starts* it:
~C-c b d~ for C, ~C-c b g~ for GTK, ~C-c b I~ for the GTK inspector,
~C-c b s~ for Guile, ~C-c R d~ for Rust and ~C-c j d~ for the JVM.

A key with nothing to drive says so, and names the key that would start a
session in the buffer it was pressed in.

If a session does nothing, ~C-c ! d~ (the doctor) says whether ~gdb~,
~lldb-dap~, ~cargo~, ~guile~, ~java~ or the adapter jar is there at all; a
missing program is a line in that report rather than a key that fails
silently.

* Guile Scheme

** The debug REPL

~C-c b s~ starts the project's REPL with the debugger set up for a hunt;
so does ~C-c g B~, which is the same command said in the topic the rest of
the Scheme keys live in.  Either way it is the REPL ~C-c g r~ starts, and
it first evaluates Guile's own debugger settings there:

#+begin_src scheme
(debug-set! stack 200000)
(debug-set! depth 200)
(debug-enable 'backtrace)
#+end_src

A deeper stack and a deeper backtrace are what make an error in a long call
chain show the frame that caused it.  They are a setting, not a constant:
~heks/scheme-debug-forms~ is the list, so a project that wants different
numbers says so without editing the command.

The rest is the workflow the REPL already gives every project:

| Key | What it does |
|-----+--------------|
| ~C-c g e~ | Evaluate the definition at point. |
| ~C-c g E~ | Evaluate the region, or the whole buffer. |
| ~C-c g b~ | Load the file into the REPL. |
| ~C-c g k~ | Interrupt a runaway evaluation. |
| ~C-c g R~ | Restart the REPL, for a fresh image. |
| ~C-c g s~ | Point the REPL at the module of this buffer. |

The habit that finds a bug fastest is the smallest loop: load the file
once, then evaluate the one definition being changed and call it at the
prompt.  The REPL is one per project, with the project root on Guile's load
path, so `(use-modules (my project))` works from the first prompt.

** Breakpoints, stepping and continuing

A Guile breakpoint is a *trap*: `,break-at-source' asks the debugger to stop
when control reaches a source location.  ~C-c b b~ in a Scheme buffer sends
that for the line at point, and pressing it again on a line that already has
one sends `,delete' for it -- the REPL's own `,traps' list is what says
which is which, so the key and the REPL cannot disagree
(`heks/scheme-breakpoint-toggle`).  A project with no REPL gets one, the way
evaluating a definition does.

When the trap fires the program is stopped at the debugger prompt, and the
same four keys the other debuggers answer to move it on:

| Key | What it does | What it sends |
|-----+--------------+---------------|
| ~C-c b n~ | Steps over the next expression. | `,next` |
| ~C-c b i~ | Steps into the call at point. | `,step` |
| ~C-c b o~ | Runs until the frame returns. | `,finish` |
| ~C-c b c~ | Runs on past the trap. | `,q` |

The key *sends the command to the prompt*, because Guile's debugger
commands are REPL commands rather than expressions: `,next` is what one
types at the prompt, and `heks/scheme-repl--command` types it there and
reads what came back.  It waits for the REPL first -- Geiser drops input
sent while an evaluation is pending -- and waits for the prompt to return
before reading, so a key pressed at the wrong moment says nothing rather
than acting on a guess.

A trap does not kill the program: `,q` resumes it, which is what makes this
a breakpoint rather than a pause.  The trap list belongs to the running
image, so a restarted REPL (~C-c g R~) starts with none -- worth knowing
before wondering why a breakpoint never fires.

** An error, and the debugger

An error raised by an evaluation does not just print: Geiser enters its
debugger, which shows the backtrace, the frame you are in, and Guile's
restarts.  The debugger's state lives in the `*Geiser Debug*` buffer, not
in the buffer the evaluation came from, so ~C-c g d~ goes to that buffer --
the point of a debugger that lives in a buffer rather than in a terminal
that has scrolled away.

~C-c g D~ is the debugger's own menu, the same one the debug buffer opens
with ~,~: backtrace, the error, the local variables, the registers, the
source buffer of the frame, the next and previous error, and quitting one
debug level.  It says so when no debugger is active rather than opening a
menu whose every entry would be refused.

The settings that decide how much the debugger shows are Geiser's:
~geiser-guile-debug-show-bt~ and ~geiser-guile-debug-show-full-bt~ are on,
so a backtrace arrives complete and with local variables, and
~geiser-guile-debug-backwards-backtrace~ puts the innermost frame last, the
way a Guile backtrace is read.

** The REPL is the debugger

Geiser's debugger is a *REPL* debugger: the program is running in the same
image as the prompt, so a frame can be inspected by evaluating in it.  That
is why there is no separate "attach" command for Scheme, and why the
recipe for a bug is the same as for a change:

1. ~C-c g B~ once, for the debug settings.
2. ~C-c g b~ to load the file under suspicion.
3. Evaluate the call that fails -- from the buffer with ~C-c g e~, or by
   typing it at the prompt.
4. When it raises, ~C-c g d~ and ~C-c g D~; the backtrace names the file and
   line, and the frames can be walked with ~n~ and ~p~.
5. Fix the definition, evaluate it with ~C-c g e~, and call it again
   without restarting anything.

** Artanis

Artanis is a Scheme web framework, so debugging one is two things at once:
the Scheme, which is debugged in the REPL above, and the running application,
whose errors arrive as a page in the browser and as lines in its log.

| Key | What it does |
|-----+--------------|
| ~C-c g W~ | Start the project's Artanis application (prefix: ask for the port). |
| ~C-c g O~ | Follow the Artanis log, tailed, at its end. |
| ~C-c g r~ / ~C-c g B~ | The project's REPL, for the code. |
| ~C-c g d~ / ~C-c g D~ | The debugger after a failing evaluation. |

The application is started from the directory holding ~ENTRY~ -- Artanis'
own name for it; ~entry.scm~ is found too (see
~heks/artanis-entry-file~) -- with ~GUILE_AUTO_COMPILE=0~ so a backtrace
names the source file rather than a compiled copy, and on the port
~heks/artanis-port~ (3000 by default).  The command line is
~heks/artanis-program~ with ~heks/artanis-arguments~, a format string whose
~%d~ is the port, for a project whose launcher differs.

The log is the first of ~log/artanis.log~, ~logs/artanis.log~ and
~artanis.log~ that exists; a project that writes none (Artanis' default is
its standard output) is followed in the ~*artanis*~ buffer ~C-c g W~
starts it in.  Either way ~C-c g O~ puts point at the end and follows it,
so the procedure is: reproduce the request in the browser, then read the
line the application wrote about it.

The code behind a failing route is debugged like any other Scheme.  Load the
module that defines the route into the REPL, call the handler with the
arguments the request would give it, and the error enters the debugger with
the frame that failed.  A route that is only wrong when the server is
running is usually a state bug: the same evaluation against the values the
handler sees is the shortest way to it.

* C, with GTK 4

** The build, and the program

A debugger needs a program with debug information, built after the last
edit.  ~C-c b d~ rebuilds when it recognises the build system, using the
same directory the program is found in:

| Build system | What the key runs |
|--------------+-------------------|
| Meson | ~meson compile -C build~ (or ~builddir~) |
| CMake | ~cmake --build build~ |
| Make | ~make~ |

For a debug build, configure once with the debug type:

#+begin_src sh
meson setup build --buildtype=debug
#+end_src

or

#+begin_src sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
#+end_src

A build directory made by an older Meson refuses the current one
(~Build directory has been generated with Meson version ...~); reconfigure
it once with ~meson setup --reconfigure build~, and the key builds again.
The debugger starts only after the build succeeds, so a failed compile is a
session that does not start -- the compilation buffer says why.

The program is the single executable in ~build/~, ~builddir/~,
~cmake-build-debug/~ or ~cmake-build-release/~; when a build holds several,
the one named after the project is chosen, and when that is not decisive the
key asks.  A prefix argument (~C-u C-c b d~) always asks, which is the
escape hatch for a layout the guess does not know.  ~heks/c-debug-program~
pins the program and ~heks/c-debug-args~ is the argument list, so a program
that needs a file or a flag at startup is a setting rather than a prompt
every time.

** The session

~C-c b d~ starts the program under gdb.  When the gdb is 14.1 or newer --
the version that speaks the Debug Adapter Protocol -- `dape` drives it, so
the session is the same buffer, the same breakpoints and the same keys as a
JVM's:

| Key | What it does |
|-----+--------------|
| ~C-c b b~ | Toggle a breakpoint on the current line. |
| ~C-c b c~ | Continue to the next breakpoint. |
| ~C-c b n~ | Step over the next line. |
| ~C-c b i~ | Step into the call at point. |
| ~C-c b o~ | Step out of the current function. |
| ~C-c b r~ | Open the debugger's REPL, for evaluating in the program. |
| ~C-c b k~ | End the session. |

An older gdb is driven by GUD, the debugger Emacs has had for decades: the
same commands, a different window.  Which one is in use is decided by
~heks/c-debug--dap-capable-p~, so nothing has to be configured either way.

** GTK's warnings, and the inspector

A GTK application's worst bugs are often warnings: a widget used after it
was destroyed, a signal connected to nothing, a size allocated for a widget
that is not there.  On a terminal they are a line that scrolls past; under
~C-c b g~ they are a breakpoint.  It is ~C-c b d~ with
~heks/gtk-debug-environment~:

#+begin_src emacs-lisp
'(("G_DEBUG" . "fatal-criticals")
  ("GSK_RENDERER" . "cairo"))
#+end_src

~G_DEBUG=fatal-criticals~ makes a GTK critical abort the program, so gdb
stops on the frame that raised it and the backtrace is the answer to "where
did this come from".  ~GSK_RENDERER=cairo~ asks GTK 4 for its software
renderer, so the session does not begin inside a GPU driver; remove it when
the renderer itself is what is being debugged.  The list is a setting, so a
project can add its own variables -- ~GDK_BACKEND~, ~WAYLAND_DEBUG~,
~GSK_DEBUG~ -- without a new command.

The launch request's environment is the program's whole environment, so the
key also passes the display variables the session inherited -- ~DISPLAY~,
~WAYLAND_DISPLAY~, ~XDG_RUNTIME_DIR~, the session bus and ~XAUTHORITY~ (see
~heks/gtk-debug-passthrough~).  Without them a GTK program started under
the debugger cannot open a window, and says ~Failed to open display~ in the
debugger's output.

~C-c b I~ runs the program with ~GTK_DEBUG=interactive~ and opens GTK's
inspector.  Its picker selects a widget on screen and the inspector shows
what that widget is: its class and CSS name, its properties, its CSS, and
the box it was allocated.  It is the first thing to reach for when a layout
is wrong and the code looks right; the debugger is for when the code is
what is wrong.

** When there is no debug information

A session that stops in a frame called ~??~ is a program built without
~-g~, or stripped.  Build a debug configuration (above), and make sure the
binary being debugged is the one that was just built -- the classic version
of this bug is a prefix argument pointing at an older copy.  A program that
was compiled with optimisation keeps its variables in registers and some of
them are shown as ~<optimized out>~; a debug build is what makes the locals
readable.

~heks/c-debug~ checks the binary before it starts: a program with no line
table is reported, with the command that would reconfigure the build for
debugging when the build system is Meson or CMake (~heks/c-debug--debug-build-hint~).
A line breakpoint in such a binary stays pending, which looks like a
breakpoint that never fires; a function breakpoint still works.

* Rust, with Cargo

** The build, the program and the debugger

~C-c R d~ debugs this crate.  It is a `dape` session like the others, so the
seven ~C-c b~ keys are the ones that move the program, and what it does
before it starts is the part a debugger cannot guess:

1. The crate is the nearest ~Cargo.toml~ walking up from the buffer
   (`heks/rust-root`), which is the crate the file belongs to rather than
   the workspace at the top of a checkout.
2. The crate is rebuilt with `cargo build`, run by `dape` and waited for: a
   session on a binary from before the edit is the classic way to chase a
   bug that is no longer there.  A build that fails is a session that does
   not start, with the compiler's own errors in the compilation buffer.
3. The program is the one the manifest says this crate produces: `cargo
   metadata --no-deps` names the binary targets and the directory the build
   goes in, so `target/debug/<name>` is an answer rather than a guess.  A
   crate with several binaries is debugged in the one the buffer is in,
   then the one named after the crate, then the first.
4. The adapter is `lldb-dap` when the machine has it, then the older
   `lldb-vscode`, then the `gdb` on the path if it is 14.1 or newer (the
   version that speaks the Debug Adapter Protocol).  None of them is a
   fallback to nothing: an older gdb runs the program under GUD with
   `rust-gdb`, which is gdb with Rust's pretty printers loaded.

The program and its arguments are settings -- `heks/rust-debug-program` and
`heks/rust-debug-args` -- and a prefix argument (~C-u C-c R d~) asks for a
file instead, which is the escape hatch for a layout the guess does not
know.

** Cargo, one key a task

The crate's own tool is the topic, and the letters are the scheme's:

| Key | What it runs |
|-----+--------------|
| ~C-c R b~ | `cargo build` |
| ~C-c R B~ | `cargo build --release` |
| ~C-c R t~ | `cargo test` (prefix: `-- --nocapture`) |
| ~C-c R v~ | `cargo check` -- the fast half of a build |
| ~C-c R l~ | `cargo clippy --all-targets` |
| ~C-c R f~ | `cargo fmt` |
| ~C-c R r~ | `cargo run`, with `RUST_BACKTRACE=1` (prefix: arguments) |
| ~C-c R c~ | `cargo clean` |
| ~C-c R a~ | `cargo add` |
| ~C-c R u~ | `cargo update` |
| ~C-c R T~ | `cargo tree` |
| ~C-c R D~ | `cargo doc --no-deps --open` |
| ~C-c R d~ | the program of this crate, debugged |

Every one of them writes to a compilation buffer, so ~C-c ! n~ walks the
errors and ~g~ runs the same command again.  Emacs reads rustc's own
output -- `error[E0308]` and the `-->` line under it, and the
`thread 'main' panicked at src/main.rs:3:5` a test or a runmode prints --
with its `rust` and `rust-panic` rules, so both are links to the line and
not text to read.

** When no breakpoint is hit

The three usual reasons, in the order they are worth checking:

- *The binary is from before the edit.*  It should not happen -- the key
  builds first -- but a `heks/rust-debug-program` pointing somewhere else
  skips the crate's own answer.
- *The code has no line table.*  A debug profile does: `cargo build` builds
  `dev` unless a profile says otherwise, and a `[profile.dev]` with
  `debug = 0` takes the line table away.  A `--release` binary has no
  useful locals, which is what `C-c R B` is for and `C-c R b` is not.
- *The line is optimised away.*  Even a debug profile inlines small
  functions; breaking on the line inside one lands on its caller, or
  nowhere.  A function breakpoint on the enclosing function is the
  reliable version when a line breakpoint stays pending.

A panic in a `cargo run` is not a debugger problem: `RUST_BACKTRACE=1` is
already set for ~C-c R r~, so the frames it came through are printed with
the panic rather than described as a variable to set and try again.

* Java, Kotlin and Maven

The JVM is debugged with `dape`'s `jdtls` configuration: Eclipse JDT LS
serves the project, and the `java-debug` plugin gives it the
`vscode.java.resolveClasspath` and `vscode.java.startDebugSession`
commands that `dape` calls for the classpath and a debug port.

The plugin is a JDT LS *bundle*, not a standalone program: it is loaded
from the jar `heks/java-debug-jar` names (or finds) by
`heks/eglot-java-init-opts` when Eglot starts JDT LS.  It is distributed
inside the VS Code Java extension and the `java-debug-adapter` mason
package; `heks/java-debug-cache-dir` is where a jar put there by hand is
found.  The project publishes no release asset, so nothing is fetched from
the network.

** One key

~C-c j d~ debugs the project of the current buffer.  It finds a Java buffer
of the project, starts Eglot/JDT LS in it if it is not running, and starts
a `dape` session that stops at the program's entry (`stopOnEntry`), so the
first stop is there and breakpoints can be set with ~C-c b b~ before
~C-c b c~ continues.

Without a prefix the main class is the one JDT LS finds.  ~C-u C-c j d~
asks for one, with `heks/jvm-main-class`'s answer as the default:
`com.example.MainKt` for `Main.kt` in Kotlin, `com.example.Main` for
`Main.java`.  Kotlin is launched through the same classpath (Maven's
`target/classes`); Kotlin *source* breakpoints depend on the adapter's
Kotlin support, and a Kotlin debug adapter is the reliable way to step
through Kotlin sources.

** Why a Java buffer

JDT LS is started for a Java file, and that buffer's Eglot server is what
`dape` asks for the classpath and the port.  A project with no Java source
has no buffer for it, and ~C-c j d~ says so instead of starting a session
that cannot work.  For a Kotlin-only project, add a Java source (or a
Kotlin debug adapter); the main-class prompt is already there.

** When it does not start

- *"No `java-debug' plugin jar found".*  Put the jar in
  `heks/java-debug-cache-dir` or set `heks/java-debug-jar`; the VS Code
  Java extension and the mason `java-debug-adapter` package both ship one.
- *"JDT LS is running without the java-debug plugin".*  The server was
  started before the jar was found; ~C-c i R~ restarts it with the bundle.
- *"Eglot did not start".*  ~C-c i E~ is the server's log; a first start
  also downloads/extracts JDT LS and imports the Maven project.
- *No main class.*  ~C-u C-c j d~ and name one; a Kotlin-only project has
  no Java main class for JDT LS to find.
- *The breakpoint is not hit.*  The session starts paused at its entry:
  set the breakpoint after that, then continue.  The class that runs is
  the one in `target/classes` (or Gradle's `build/classes`), so compile
  before the session when the source changed.  Kotlin coroutines and
  inline functions make one source line several frames.
- *The app is waiting, and nothing connects.*  That is `stopOnEntry` doing
  its job; if `dape` never connects, the JDT LS log (~C-c i E~) says why.
- *The port is taken.*  JDT LS chooses the debug port with
  `vscode.java.startDebugSession`; another JVM on that port is a server
  that needs restarting (~C-c i R~).
